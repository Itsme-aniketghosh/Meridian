How Meridian works

Meridian finds every call to an API that's being retired, who owns it, how risky it is and which teams are stuck waiting on each other. Rules decide the facts; LLM agents only write them up, and a fact gate checks every word. The tools cut the noise so a model reads only what matters, and when a tool comes back empty, the graph walkers go straight to the code graph. Self-improving loops retrain the model, let policies and walkers compete and correct the agents' text. Most of them need real users to turn.

Self-improving loops

Five loops let Meridian get better as it runs: the model, the auditors, the walkers, the writing agents and the diff drafter. Each changes production only through a rule written in advance, and the ↻ badges in the diagram show where each one runs. A sixth, an LLM that writes policies, was cut.

↻1

The model retrains itself

built: model.refresh --every 24; runs when a new block is published

Nothing is decided by hand. A model that loses stays registered with its reason, and the winner is the bar for the next cycle. CI runs the same steps on every push.

↻2

Auditor policies compete

built; checked in simulation; 0 live matches until people use it

The team sees the champion's ranking most of the time and a challenger's the rest. Whichever ranked the true reason higher wins the match. The guard used to promote a no-better policy by luck 87% of the time; now it's 4.0%.

↻3

walk-v1: the walkers learn where to look

built in #129; scored once stall verdicts arrive

walk-v1 follows the auditor's ranking: it visits first the upstream team with the most evidence for the top reasons. Rules only, no model picks a step. On the real block 16 of 68 stalls drew it, and no walk differed yet.

↻4

The agents correct themselves

built; the ladder runs per task, a person makes the fix

Inside each task the ladder retries on a bigger model, then ships the template. Across runs, the fallback rate shows where text fails: consumer texts fell back 41 of 68, the cause was fixed (#122), and the cached answers re-gated to 0 of 68 at $0. The orchestrator's plans run the same check: a refused plan gets the rules plan.

↻5

The diff drafter learns each owner

built; tested on the fixture; no real outcomes yet

A wrong diff costs the owner more than no diff, so the drafter waits for the owner's own lines before it drafts the rest.

↻6

An LLM writes new policies

cut (gap 22); phase 3

The guard it needed (luck ≤ 5%) is in place. The agent isn't: every new challenger is another chance at a lucky promotion, so it waits for live matches.

Guardrails

  • Code decides, models write. Facts come from rules over the block. An LLM never decides a fact.
  • Every plan ends. One planning call, a closed menu, each step once. A bad answer gets the rules plan.
  • Code decides when a tool failed: an error, a hang, nothing usable, or two gate misses. Then the walkers run.
  • Walkers are boxed in: read-only, named queries only, 3 teams, 2 hops, 24 queries per stall.
  • No people in facts. A fact with an email is refused before a prompt is built.
  • Every answer is cached by model, prompt version and facts, so reruns cost nothing and match byte for byte.
