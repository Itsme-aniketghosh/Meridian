# Pass bars · Oct 26 · written before any of these changes ran

docs/05-test.md: "Pass bars fixed before the run. Changing one needs a commit saying why." These are the bars for three fixes to signals that are weak on real data (report, Appendix C). Each rule below is defined here, before it is scored, so it can't be fitted to the answer.

## 1. P1 Drift: the resolver at push time

**Change.** `pushcheck.head_sites` runs the pipeline's own resolver (`resolve.Repo.resolve_candidate`) on the changed files' candidates and drops the ones it calls `dropped` (a look-alike: the name lands on a parameter or a local), exactly as join does. Unresolved names (`ast_unresolved`, e.g. no Django checkout in CI) stay, as join keeps them.

**Bars.**
- (a) The 21-commit replay (each pinned SHA's next commit, scope limit lifted): P1 precision ≥ 0.80 (05-test), and all 4 true Django hits (`test_legacy_aliases`) still found.
- (b) Held out, never looked at before: every first-parent Django commit after the conversion commit `c651331b34` that adds or removes a line with a tracked `ugettext*` name (`git log -G`). A commit whose added lines call a tracked name must get P1 (recall 100%); P1 on a commit that adds none is a false hit (precision ≥ 0.95, 05-test).

## 2. T3 vague ticket: bug without a reproduction

**Change.** Apache Jira never writes "done when", so the done-condition check fires on every Spark ticket. 05-test's real test for a ticket check: does it pick the bugs that end **Incomplete** or **Cannot Reproduce** rather than **Fixed**? The check, defined now: a Bug is vague when its description is empty, or has none of: a `{code}` or `{noformat}` block, a stack frame (`at x.y(File:n)` or `File "…", line n`), or one of the words *reproduce*, *repro*, *steps*.

**Bar.** On Spark Bugs resolved from 2020-01-01 on, as Fixed (negative) or Incomplete / Cannot Reproduce (positive): the check's precision beats 05-test's baseline, description length, flagging the same number of bugs (shortest descriptions first). Recall is reported. Caveat: descriptions are as of the pull, so a ticket edited after it was resolved could leak.

## 3. GitLab cross-team waits: the label rule

**Change.** Today's rule ("the two issues carry different `group::` labels") keeps 116 links, precision 0.14, recall 0.30 against the gold set. The new rule, defined now, adds timing evidence of an actual wait to the label rule: the blocker closes after the link was added, and the blocked issue closes after the blocker (or is still open).

**Bar.** Against `labels/gitlab_cross_team_blocks.csv` (verdict `wait` is positive; `no`, `planned` negative; `unclear`, `partial`, `no_evidence` left out): precision ≥ 0.50 with recall ≥ 0.30. This is **not** 05-test's 0.90 bar: the gold set is model-read (0 of 262 human verdicts), so any number here is provisional until a person checks the gold set.
